# Connectly cross-platform security and release plan

**Updated:** 2026-11-01  
**Branch:** phase-1-auth-friends  
**Status:** UI roadmap added; backend and native integrations are not enabled.

## 1. Multi-factor authentication

### Email one-time codes
Use a short-lived, single-use email challenge with rate limits, expiry, attempt limits, resend cooldown, and server-side verification. Email OTP is an additional verification step only when the sign-in flow explicitly requires it; ordinary email OTP sign-in must not be misrepresented as MFA.

Supabase Auth's supported MFA factors and the project's configured email provider must be checked before implementation. If email is not a supported MFA factor for the chosen configuration, implement a separate server-verified challenge with abuse controls rather than a client-only code check.

### Face / fingerprint authentication
Use WebAuthn passkeys / platform authenticators. Android, iOS, Windows and macOS may ask the device to verify with its available screen lock, fingerprint or face unlock. Connectly should receive a cryptographic assertion, never a face scan or fingerprint image. Provide recovery codes or another secure recovery method and warn about new-device sign-in.

Acceptance: enrol, sign-in challenge, revoke, recovery, rate-limit, replay and cross-device tests.

## 2. Push notifications

Target support:
- Android Chrome and installed PWA: Web Push where supported.
- Desktop Chrome/Edge/Firefox: Web Push where supported.
- iPhone/iPad: Web Push for eligible installed Home Screen web apps on supported iOS versions.
- Native Android/Windows/Linux wrappers: native notification integration and permission prompts as appropriate.

Required backend:
- VAPID application server keys stored only as server secrets.
- Per-device push subscriptions with authenticated ownership and revocation.
- Server-side delivery worker / Supabase Edge Function.
- User preferences for message, friend-request and call notifications.
- Generic notification text by default; never include message plaintext in push payloads for E2EE chats.
- Expired subscription cleanup, retry/backoff, rate limits and abuse controls.

Push delivery is not implemented by the settings UI alone. It requires server secrets, a delivery worker and real device tests.

## 3. UI and Liquid Glass

The latest CSS update reduces visual density, improves text hierarchy and increases transparency in the Liquid Glass theme. Keep text contrast and fallback surfaces readable on devices without backdrop-filter support. Avoid making every surface fully transparent; controls and message text must remain legible.

## 4. Android, Windows and Linux deliverables

Recommended approach: Tauri 2 wrappers that load the deployed Connectly web app, with platform-specific notification bridges where required.

- Android: signed APK (and optionally AAB) via Tauri Android tooling.
- Windows: signed installer / executable bundle via Tauri bundling.
- Linux: .deb package via Tauri bundling.

Prerequisites before generating release artifacts:
1. Stable HTTPS production URL and deployment health checks.
2. Tauri shell project, app identifiers, icons, deep-link handling and platform permissions.
3. Android signing keystore and secrets stored in GitHub Actions secrets (never commit keys).
4. Windows signing certificate if trusted signed distribution is required.
5. Linux package metadata and dependency checks.
6. Automated build matrix, artifact retention and install/launch smoke tests on real devices.

A GitHub workflow must not publish placeholder or unsigned files as production-ready installers. Build artifacts are not generated by this planning/UI commit.

## 5. Release gates

- MFA: email challenge and passkey flows independently tested.
- Push: Android, desktop browser and iOS PWA permission/delivery tested on real devices.
- UI: mobile, desktop, light, dark and Liquid Glass visual regression checks.
- Packaging: APK, Windows installer and DEB built from the same tagged commit; install and launch smoke tests pass.
- Security: no secrets in client bundles or repository; E2EE remains labelled disabled until its separate acceptance gates pass.
